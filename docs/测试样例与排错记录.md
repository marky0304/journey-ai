## 第二部分：排错记录

### Bug #1 — Celery 任务中 asyncio.run() 嵌套事件循环崩溃

| 项目 | 内容 |
|------|------|
| **发现日期** | 2026-05-13 |
| **严重级别** | CRITICAL（阻塞主流程） |
| **影响范围** | 所有行程规划任务 |
| **发现阶段** | 后端自测 |

#### 现象

Celery worker 日志持续报错，所有规划任务全部失败，Redis 中 task 状态卡在 `processing`：

```
[2026-05-13 14:32:17] ERROR celery.worker.strategy:
Task planning.run_trip_planning[abc-123] raised unexpected:
RuntimeError('asyncio.run() cannot be called from a running event loop')
```

#### 复现步骤

1. 启动 Celery worker：`celery -A app.tasks.celery_app worker --pool=gevent`
2. 通过 API 提交任意合法行程规划请求
3. 观察 worker 日志

> **必现率**：100%（gevent/eventlet pool 下）

#### 排查过程

1. **定位崩溃点**：`planning_task.py:55` — `asyncio.run(run_trip_pipeline(...))`。`run_trip_pipeline` 内部大量 `await` 调用（coordinator_node → asyncio.gather 并行四个子 Agent → strategy_node），确实需要事件循环。

2. **分析冲突根源**：Celery 使用 `gevent` pool 时，worker 进程本身运行在 greenlet 协程上下文中。`asyncio.run()` 尝试创建**新的事件循环**，与 gevent 已有的 hub loop 发生冲突。gevent 通过 monkey-patch 接管了标准库的 IO 操作，而 asyncio 期望独立的原生事件循环 —— 两者在同一线程中无法共存。

3. **验证假设**：临时切换为 `--pool=prefork` 后任务正常执行，确认问题限定在 gevent/eventlet pool 与 asyncio 的兼容性上。

#### 修复方案

将 `asyncio.run()` 替换为独立线程内运行事件循环的方式，规避 gevent 线程级冲突：

```python
# planning_task.py — 修复前（第 55 行）
result = asyncio.run(run_trip_pipeline(initial_state))

# 修复后
import concurrent.futures

def _run_async_in_thread(coro):
    """在独立线程中运行 asyncio 协程，避免与 gevent hub loop 冲突"""
    def _runner():
        return asyncio.run(coro)
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
        return executor.submit(_runner).result()

result = _run_async_in_thread(run_trip_pipeline(initial_state))
```

同样修复第 68 行 `asyncio.run(save_trip_to_db())`。

#### 验证结果

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| gevent pool | 100% 失败 | 0% 失败 |
| prefork pool | 正常 | 正常 |
| 任务平均耗时 | - | 差异 < 200ms |

### Bug #2 — Strategy Agent 输出 JSON 中 budget 字段为空导致前端白屏

| 项目 | 内容 |
|------|------|
| **发现日期** | 2026-05-15 |
| **严重级别** | HIGH（前端白屏，用户不可用） |
| **影响范围** | 约 30% 的规划结果 |
| **发现阶段** | 前后端联调 |

#### 现象

行程规划成功（后端返回 200），但前端结果页白屏。浏览器控制台报错：

```
TypeError: Cannot read properties of undefined (reading 'min')
    at TripSidebar.tsx:47
```

#### 复现步骤

1. 提交目的地为"西藏"、预算范围 5000-8000 的请求
2. 等待规划完成（Redis 中 `trip_data` 已写入）
3. 前端跳转至 `/trip-result` 后立即白屏

> **必现率**：约 30%（取决于 LLM 输出格式波动）

#### 排查过程

1. **检查 Redis 中的 trip_data**：

   ```json
   {
     "destination": "西藏",
     "dates": {"start": "2026-07-01", "end": "2026-07-07"},
     "budget": {},
     "preferences": ["自然风光", "摄影"],
     "days": [ /* 正常 */ ]
   }
   ```

   `budget` 字段为空对象 `{}`，而前端期望 `{"min": 5000, "max": 8000, "currency": "CNY"}`。

2. **追溯源头**：`graph.py` 的 `extract_trip_from_final_plan` 直接透传 LLM 输出的 JSON，未对顶层字段做结构性校验。

3. **根因定位**：Strategy Agent 的 prompt（`strategy.py:10`）中 budget 字段描述为 `"budget":{"min":0,"max":0,"currency":"CNY"}`，但 DeepSeek 模型在部分响应中会省略认定为空值的字段。中间层 `extract_trip_from_final_plan` 缺少字段兜底补全逻辑，导致异常数据直达前端。

#### 修复方案

**后端** — `extract_trip_from_final_plan` 增加 budget 字段兜底：

```python
# graph.py — 在 extract_trip_from_final_plan 函数中新增
budget = parsed.get("budget", {})
if not isinstance(budget, dict) or not budget:
    parsed["budget"] = {
        "min": parsed.get("budget_min", 0),
        "max": parsed.get("budget_max", 0),
        "currency": parsed.get("currency", "CNY"),
    }
```

**前端** — 增加防御性空值处理：

```typescript
// TripSidebar.tsx — 修复前
const budgetMin = trip.budget.min;
const budgetMax = trip.budget.max;

// 修复后
const budgetMin = trip.budget?.min ?? 0;
const budgetMax = trip.budget?.max ?? 0;
```

#### 验证结果

- 模拟 `budget: {}` 的异常数据，前端不再白屏，显示"预算：待确认"
- 后端 100 次模拟请求中 budget 缺失率从 30% 降至 0%

### Bug #3 — Redis 连接池耗尽导致任务状态轮询超时

| 项目 | 内容 |
|------|------|
| **发现日期** | 2026-05-17 |
| **严重级别** | MEDIUM（并发场景功能降级） |
| **影响范围** | 并发 ≥ 5 任务时状态查询失败 |
| **发现阶段** | 压测 |

#### 现象

并发 10 个规划任务时，前端轮询 `GET /api/trip/status/{task_id}` 接口间歇性返回 500：

```json
{ "detail": "ConnectionPool exhausted - cannot acquire connection" }
```

#### 排查过程

1. **检查 Redis 连接配置**：`core/redis.py` 中连接池 `max_connections` 被设为默认值 10。

2. **分析连接占用情况**：
   - 每个 Celery 任务通过 `celery_app.backend.client` 获取一个 Redis 连接
   - 连接持有整个任务生命周期（约 15-30 秒，Agent 链路耗时）
   - 并发 10 个任务 = 10 个连接被长时占用

3. **API 端连接需求**：FastAPI 的状态查询 API 每次请求需要从**同一连接池**获取连接。连接池满时，新请求无法获取连接，直接抛异常。

4. **根因**：Celery backend 与 API 服务共享同一个 Redis 连接池，缺乏隔离。连接池大小 10 不足以支撑两端并发需求。

#### 修复方案

为 Celery backend 与 API 服务使用独立连接池：

```python
# core/redis.py — 修复后
import redis.asyncio as aioredis
from app.config import settings

_api_pool = aioredis.ConnectionPool.from_url(
    settings.redis_url, max_connections=20, decode_responses=True,
)

_celery_pool = aioredis.ConnectionPool.from_url(
    settings.redis_url, max_connections=30, decode_responses=True,
)

def get_api_redis():
    return aioredis.Redis(connection_pool=_api_pool)

def get_celery_redis():
    return aioredis.Redis(connection_pool=_celery_pool)
```

#### 验证结果

- 并发 50 任务压测，API 状态查询零失败
- 连接池监控显示峰值利用率 65%，有充足余量

### Bug #4 — 日期组件在中文环境下显示英文

| 项目 | 内容 |
|------|------|
| **发现日期** | 2026-05-18 |
| **严重级别** | LOW（UI 本地化不完整） |
| **影响范围** | 日期选择器组件 |
| **发现阶段** | 前端自测 |

#### 现象

日期选择器弹出后，星期标题显示 "Su Mo Tu We Th Fr Sa"，选中日期格式化输出为 "June 1, 2026"，与整体中文 UI 不协调。

#### 排查过程

1. **检查 Calendar 组件**：`components/ui/calendar.tsx` 使用 shadcn/ui 的 `<Calendar>`，底层依赖 `react-day-picker`。
2. **定位原因**：`react-day-picker` 默认 locale 为 `enUS`，需要在组件 props 中显式传入 locale 配置。

#### 修复方案

```tsx
// components/ui/calendar.tsx
import { zhCN } from "date-fns/locale";
import { format } from "date-fns";

<Calendar
  locale={zhCN}
  formatters={{
    formatCaption: (date) =>
      format(date, "yyyy年MM月", { locale: zhCN }),
  }}
/>
```

#### 验证结果

- 星期标题显示"一 二 三 四 五 六 日"
- 选中日期格式化输出"2026年06月01日"
