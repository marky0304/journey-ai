# 排错记录：AI 智能行程规划系统

## 项目背景

基于大语言模型的多 Agent 旅行规划系统。用户输入目的地、日期、预算、偏好，系统自动生成包含交通、住宿、景点、餐饮的完整行程。

初始架构：

```
Coordinator(LLM) → Transport | Accommodation | Attraction | Dining（四 Agent 并行）→ Strategy(LLM) → 输出
```

技术栈：FastAPI + LangChain + Celery + Redis + PostgreSQL + ChromaDB（向量库）+ BGE-small-zh-v1.5（嵌入）

---

## 问题一：规划超时 —— 遗传算法 + 切普通模型

### 现象

前端提交行程规划后，超过 2 分钟无响应。Celery 任务状态卡在 `PENDING`，后端日志频繁出现：

```
httpx.ReadTimeout: The read operation timed out
```

用户需反复重试才能偶尔成功。

### 排查

初始采用 DeepSeek 强推理模型，在 `backend/app/agent/graph.py` pipeline 各阶段埋点测耗时：

| 阶段 | 平均耗时 |
|------|---------|
| Coordinator（LLM 做预算分配 + 总结） | ~8s |
| 4 个领域 Agent 并行（等最慢的那个） | ~25s |
| Strategy（汇总生成最终行程） | ~15s |
| **合计** | **~48s** |

强推理模型的 API 响应不可靠，高峰期单次调用可能超过 60s。httpx 配置了 2 次重试，最坏情况一个 Agent 死等 180s，整个链路断开。

另一个明显浪费：**Coordinator 用 LLM 做预算分配**。把"美食多少、住宿多少"这种比例拆分交给大模型，耗时 ~8s 输出还经常不合理。

### 根因

- Pipeline 3 层串行，每层都是网络往返
- 强推理模型本身推理慢，高峰期排队更不可控
- 预算分配是确定性数学问题，不该走 LLM

### 解决

**措施一：遗传算法替代 LLM 做预算分配**

新增 `backend/app/agent/budget_optimizer.py`：

- 种群 200，迭代 150 代，SBX 交叉 + 多项式变异
- 偏好 → 品类权重映射表（手调："美食" → dining ×1.70，"文化" → attraction ×1.45 等）
- 耗时：~8s → ~0.2s

**措施二：切换普通 Chat 模型**

将模型从强推理模型换为普通 Chat 模型（响应快但推理能力弱于强推理模型）。Chat 模型单次调用 2-5s，并行阶段总等待时间大幅缩短。

### 结果

- 总耗时 ~48s → ~15-20s（-60%+）
- 预算分配从 LLM 随机 → GA 确定性输出
- **代价**：Chat 模型虽然快，但推理能力远不如强推理模型，幻觉问题随之暴露

## 问题二：Chat 模型幻觉 ——优化 RAG + Prompt + 降温

### 现象

切到普通 Chat 模型后速度达标了，但生成的行程开始频繁出现编造：

- 不存在的酒店名（"三亚海棠湾 XX 度假酒店"）
- 虚构航班号（"CZ6789 08:00-11:30"）
- 拼凑的餐厅名，地图/点评完全搜不到
- 门票价格随意写，和实际偏差 50%+

### 排查

检查四个领域 Agent 的 Prompt（`backend/app/agent/transport.py` 等），发现：

1. 虽然系统一开始就有 RAG（ChromaDB 向量检索 + BGE 嵌入），但**仅用于聊天场景**（`chat_agent.py`、`context_engine.py`），**规划流程的四个核心 Agent 并没有接入 RAG**。Agent 生成内容全凭模型自身参数化知识。

2. Prompt 中写有"尽量用完预算"——模型为了填满额度，倾向于编造高价选项。

3. Chat 模型的参数知识储备和推理严谨度明显弱于强推理模型。

### 两难

| 选项 | 优点 | 缺点 |
|------|------|------|
| 换回强推理模型 | 幻觉少 | 超时问题会复现 |
| 留在 Chat 模型 + 加强约束 | 保持速度 | 需大幅优化检索和 Prompt |

**选择了后者**——不在模型能力上妥协，在检索质量和约束强度上补齐。

### 解决

**措施一：RAG 优化 —— 纯向量检索 → 混合检索**

原有 RAG 只做单一余弦相似度检索，对中文关键词（地名、景点名）的召回不够精确。改进为**向量 + BM25 混合检索**（`backend/app/services/vector_store.py`）：

```
最终分数 = 向量相似度 × 0.7 + BM25 关键词匹配 × 0.3
```

其中 BM25 采用中文 bigram 分词，对地名、专有名词的匹配效果显著优于纯向量检索。

同时将 RAG 从聊天专用拓展到规划流程：四个领域 Agent 的 Prompt 中注入检索到的相关游记片段，让模型在真实数据约束下生成。

检索流程：
```
用户目的地 + 偏好
    │
    v
VectorStore.hybrid_search(query, top_k=3)
    │  (cosine ×0.7 + BM25 ×0.3)
    v
取回真实游记片段（如："三亚亚龙湾 XX 酒店，淡季 600/晚"）
    │
    v
注入各 Agent Prompt 的「参考知识」段落
    │
    v
LLM 在真实数据约束下生成
```

**措施二：修改 Prompt**

- 删除"尽量用完预算"
- 改为"优先使用参考知识中的真实选项，不确定时标注 `confidence: low`"

**措施三：加强硬约束**

Coordinator 生成的 `constraints` 字典下发给各 Agent（每品类预算上限、偏好权重），Agent 必须在约束框架内生成。

**措施四：降低温度**

temperature 0.3 → 0.2，JSON 结构化输出模式进一步收紧随机空间。

### 结果

- 幻觉率约 40% → 约 10%
- 速度不受影响（检索 <5ms，几乎无额外延迟）
- 剩余幻觉多为地理位置偏移（酒店对但区域描述不准），后续可对接 OTA API 做最终校验

## 问题三：ChromaDB C 扩展 Windows 崩溃 —— 换纯 Python 库

### 现象

系统一直在用的向量库 ChromaDB，在 Windows 11 + Python 3.12 环境下启动后端时报错：

```
ImportError: DLL load failed while importing _hnsw: 找不到指定的模块
```

尝试装兼容版本的 wheel 后勉强跑起来，但运行一段时间随机崩溃：

```
Windows fatal exception: access violation
  File "...\chromadb\segment\impl\vector\local_hnsw.py", line XX in _search
```

### 排查

依赖链路：`chromadb 0.5.23` → `hnswlib`（C/C++ 编译扩展 `.pyd`）。

`hnswlib` 官方预编译 wheel 只支持到 Python 3.11。项目用 Python 3.12，没有匹配 wheel → pip 尝试源码编译 → Windows 缺失 MSVC 工具链 → 失败。装了个 Python 3.11 的 wheel 强制使用，底层 Visual C++ Redistributable 版本不匹配，导致运行时段错误。

### 根因

ChromaDB 底层 hnswlib 是 C 扩展，对 Windows + 新版 Python 的预编译覆盖不完整。源码编译又依赖 MSVC。Windows 环境下 Python 科学计算生态的经典痛点。

### 解决

**彻底移除 ChromaDB，自研纯 Python 向量数据库**（`backend/app/services/vector_store.py`）。

跟问题二中优化的混合检索逻辑完全保留，只是底层存储从 ChromaDB 换成自研实现：

| 组件 | 原方案（ChromaDB） | 新方案（自研） |
|------|-------------------|---------------|
| 向量存储 | hnswlib C 扩展 | NumPy `ndarray`（N × 512, float32），全内存 |
| 持久化 | ChromaDB 内嵌 SQLite | JSON 文件 `./vector_data/vectors.json` |
| 分块 | ChromaDB 内置 | 512 字符滑动窗口，句子边界对齐 |
| 相似度 | hnsw 近似搜索 | `np.dot` / `np.linalg.norm` 精确余弦 |
| 混合检索 | 无（仅向量） | 向量 ×0.7 + BM25 ×0.3（中文 bigram） |
| 过滤 | ChromaDB metadata filter | `where={"user_id": "xxx"}` 手动过滤 |
| 去重 | ChromaDB 内置 | 父文档 ID 去重，留最高分块 |

嵌入模型保持三级联 fallback（`backend/app/services/embedding_service.py`）：

```
ModelScope BGE-small-zh-v1.5 (512维，首选)
  → HuggingFace BGE-small-zh-v1.5（备选一）
  → HuggingFace paraphrase-multilingual-MiniLM-L12-v2（备选二）
  → SimpleChineseEmbedding（兜底，字符 n-gram hash，离线可用）
```

### 结果

- 零 C 扩展依赖，Windows/Linux/macOS 全部兼容
- 启动时间 ~3s → <0.5s
- 1 万条知识 ~50MB 内存，检索 <5ms
- 10 万级以上可考虑迁 pgvector 或 Milvus Lite

---

## 连带修复：异步容错

优化 RAG 检索逻辑时发现，聊天上下文构建（`context_engine.py`）用 `asyncio.gather()` 并行取偏好/知识/元数据/历史。`return_exceptions=False`（默认值），一个子任务失败（Redis 断开、向量文件被锁），其余三个结果全丢弃，用户收到空白回复。

修复：`return_exceptions=True` + 每个子任务 `try/except` 兜底返回空默认值。

## 因果链总结

```
强推理模型超时
    │
    ├── GA 替代 LLM 预算分配
    └── 切换普通 Chat 模型提速
         │
         v
    Chat 模型幻觉严重
         │
         ├─ 想换回强推理 ──✘ 超时问题会回来
         │
         ├── 优化已有 RAG：纯向量 → BM25+向量混合检索
         ├── 修改 Prompt + 加强硬约束
         └── 降低温度
              │
              v  （一切正常，速度和质量都达标）
              │
         ── 一段时间后 ──
              │
              v
         ChromaDB C 扩展在 Windows 下崩溃
              │
              v
         自研纯 Python（NumPy + JSON）向量数据库 ✓
```

| 阶段 | 问题 | 约束 | 方案 |
|------|------|------|------|
| 1 | 强推理模型超时 | 不能接受 >30s | GA + 切 Chat 模型 |
| 2 | Chat 模型幻觉严重 | 不能回退强推理（超时） | 优化 RAG 混合检索 + 降温度 + Prompt 重构 |
| 3 | ChromaDB C 扩展崩溃 | Windows 兼容性 | 自研 NumPy 向量库 |

### 核心教训

1. **模型速度 vs 推理能力是一个 trade-off**：不能既要秒回又要严谨推理。弱模型的短板可以用高质量 RAG 补齐。
2. **RAG 不是"有就行"，检索质量决定效果**：纯向量检索对中文专有名词召回不足，BM25 混合后才有质的提升。
3. **确定性计算不要走 LLM**：预算分配用 GA，又准又快又不花钱。
4. **Windows 环境优先纯 Python 依赖**：C 扩展的跨版本兼容性是定时炸弹，小规模数据自研方案完全够用。
5. **每个改动都可能牵出新问题**：本来是优化速度和幻觉，结果把底层的 ChromaDB 兼容性问题也暴露了出来。
